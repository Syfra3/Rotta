# Rotta benchmarks and telemetry: comparison with Gentle-AI and Gentle-Shell

## Executive assessment

Rotta has a useful **retained outcome-record validator**, but not yet an end-to-end workflow benchmark or an automatic, measured improvement loop. Gentle-AI supplies the most relevant benchmark pattern: deterministic, isolated CLI journeys plus separately labeled observations of a real agent session. Gentle-Shell supplies the most relevant instrumentation pattern: per-response token/cache coverage, child-agent observations, and local session usage summaries. Neither project's anonymous aggregate runtime feed alone can calculate Rotta's task-level acceptance funnel: that requires a **local, stable work ID and ordered lifecycle events**.

**Answer to the practical question:** Tracking the proposed numbers alone will **not** tell us whether Rotta works well. We must connect each outcome to its original acceptance checks and final delivered behavior; record exactly where a run waited, failed, recovered or stopped; and distinguish a Rotta workflow defect from a task defect, host failure or missing observation. Start with a **local-only monitor on this computer**, plus repeatable benchmarks that reproduce suspected workflow issues. No collector, cloud export, account, network service or Notion integration is needed. These repositories provide patterns and contracts, **not measured evidence that one workflow is faster or better than another**.

## What to reuse, and where the boundaries differ

1. **Gentle-AI: two benchmark lanes.** Its `run` lane drives the product binary with clean home/config/git fixtures; `record` + `analyze` measures an actual agent's CLI invocations. Both use one friction classifier but the tool refuses to compare driven and observed results. The seven reported dimensions are human prompts, manual authorization tokens, commands to completion, block classes, recovery round trips, model runs and human-facing stderr bytes ([bench README](https://github.com/Gentleman-Programming/gentle-ai/blob/70d065688b98382fa7b20f9036668e0bdf3db4d8/bench/README.md)). Model runs are a **proxy** in observed mode because a CLI shim cannot see the host's model calls ([analyzer](https://github.com/Gentleman-Programming/gentle-ai/blob/70d065688b98382fa7b20f9036668e0bdf3db4d8/bench/analyze.go)). Adapt this split: Rotta's installed host workflow needs scenario-driven host adapters, while the `rotta` Go CLI can have its own portable offline journey corpus. A passing corpus declaration/unit test must not be mistaken for a driven host run.
2. **Gentle-Shell: local usage and source coverage.** `/gentle:stats` reads existing Pi session history for tokens, cost, models and activity without persisting a new stats database ([extension](https://github.com/Gentleman-Programming/gentle-shell/blob/9eac7ae80d9df0447e4f4980d0f2a0e98a6deccd/extensions/gentle-stats.ts)); its top-level scan excludes nested runs, so child usage needs separate capture/deduplication. Child observations use only available final assistant responses, with selected model/effort distinct from observed response model/effort ([child adapter](https://github.com/Gentleman-Programming/gentle-shell/blob/9eac7ae80d9df0447e4f4980d0f2a0e98a6deccd/lib/runtime-metrics-children.ts)). Rotta's [Pi extension](../assets/pi/rotta-extension.ts) already reports delegate elapsed time/model in tool details, but that display is not a durable cross-host usage record.
3. **Gentle-AI/Gentle-Shell: data-quality pattern.** Their [runtime contract](https://github.com/Gentleman-Programming/gentle-ai/blob/70d065688b98382fa7b20f9036668e0bdf3db4d8/docs/telemetry.md) sends sanitized bounded rows once, best effort, without prompt/code/path, task/session IDs, client queue or retry. Each token field records whether source usage is reported, unavailable or unsupported. That anonymous design is useful inspiration for typed availability, but it **cannot** attribute a first-pass result to a specific task. A local Rotta monitor should retain the task joins locally and has no need for a remote transport.
4. **Rotta: preserve what already works.** `rotta workflow benchmark --input ... --worktree ... --id ...` reads exactly three JSON records and writes immutable results under `reports/benchmarks/<id>` ([CLI](../cmd/rotta/main.go), [runner](../internal/workflow/outcome_benchmark_runner.go)). Records require matching task/policy/baseline/provider/model/family/integration/permission/acceptance fingerprints across runs. The result's own conclusion says *fixture semantics only; no performance trend claim*. Do not repurpose `passed` as an acceptance-rate or cycle-time improvement. Extend via a versioned measured-result schema or a companion evaluator; keep old fixture results interpretable.

## Proposed Rotta metric contract

**Unit of analysis:** one stable, approved/user-visible *work outcome*, not a session, child agent, scenario, message or PR. The same work ID persists across handoffs/resumes/renames. A cohort must pin task fixture or stratified task class, repository baseline, Rotta policy version/digest, host/version, provider/model/effort, integrations, permission profile and acceptance checks. Report Fast and Strict separately; pair same fixtures for before/after comparison. A changed model or task is a separate cohort, not evidence of a workflow speedup. Keep `source`, `coverage`, `derivation` (`measured`, `proxy`, `unavailable`) and reasons on each metric; absence is never zero.

| Metric | Operational definition / denominator | Minimum event evidence |
| --- | --- | --- |
| First-pass acceptance rate | Outcomes with **all required acceptance checks passed before the first independent review** and **zero admitted blockers in that initial review**, divided by outcomes reaching an initial review with required checks observable. Also report pre-review return-to-implementer rate separately; do not silently exclude those from the broader started-work funnel. | Check-to-diff identity and result, initial-review ID/timestamp, blocker IDs, first handoff, cohort and missing-evidence count. |
| Objective cycle time | Active elapsed milliseconds from first authorized task start to first **delivered/verified user-visible outcome**, excluding separately measured user waiting and external outages. Also show wall clock and p50/p90; unfinished work is censored and counted. Do not use sum of child wall times as parent elapsed time when work overlaps. | Start/end timestamps and clock source; phase intervals and pause reasons; delivered/verified terminal evidence. |
| Context complexity | A **vector**, not an opaque score: initial instruction/capsule bytes or actual tokens, distinct relevant files/symbols read, context compactions, child handoffs, repeated reads and tool-output bytes. Context-window occupancy is a snapshot, not total spend. | Host-observed prompt/context data where supported; local tool/compaction counters, capsule sizes and explicit unknowns. |
| Review friction | Per accepted outcome: initial reviews, delta reviews, unique reviewer dispatches, admitted blockers, correction rounds, reopened finding IDs, review-to-closure active time and human questions. Separate review calls from reviews completed, and accepted outcomes from all started work. | Review/finding/correction lifecycle events with stable IDs and timestamps. |
| Funnel | For each cohort, counts from **started → scope approved where required → implementation handoff → required checks pass → initial review → no blockers or repaired → verified → delivered**. At each edge show entrants, exits, drop-offs by reason, waiting/censored and terminal `completed`, `blocked`, `safely stopped`. Never infer an unobserved stage from a later event. | Ordered versioned state transitions tied to work ID and record revision. |
| Tool/model efficiency | Per outcome and by phase/role/host: tool call attempted/completed/failed/denied, retry counts and duration; model requests/responses, input/output/reasoning, cache read/write and cost **only when provider/host reports them**; cache hit share = reported cache-read / (reported input + reported cache-read) only where token semantics are comparable. | Host adapters with deduped event IDs, model/effort evidence, per-field coverage; exclude synthetic probes and distinguish tool retries from review iterations. |

Guardrails alongside every efficiency comparison: acceptance pass rate, escaped regressions, unresolved blockers, evidence completeness and human intervention. Avoid one composite score that can hide worsened delivery quality or more dead ends ([Gentle-AI dimension model](https://github.com/Gentleman-Programming/gentle-ai/blob/70d065688b98382fa7b20f9036668e0bdf3db4d8/bench/metrics.go)). Do not count a missing report as a successful zero-cost task.

## Local diagnostic monitor: how we would know if Rotta works

Two connected views are necessary. The **work-outcome view** tells whether Rotta delivered what the user asked, with real acceptance checks tied to the final diff/consumer path; the **execution trace** explains the cost and failure path. A green test, a reviewer approval or low token usage alone is not proof of delivery. A workflow run is healthy only if the required checks passed, blockers closed, final user-visible outcome was verified/delivered, and the evidence is attributable to that work ID. Real tasks can remain legitimately blocked; report them accurately rather than treating every stop as a workflow defect.

| Diagnostic question | Evidence to collect locally | What a finding would mean (hypothesis, not automatic cause) |
| --- | --- | --- |
| Is Rotta actually completing objectives? | Started vs delivered work, check coverage/results on final diff, delivered/integrated/verified statuses, incomplete or reopened work | High initial-review approval with low delivered rate suggests foundation-only completion, missing integration or a misleading terminal report. Inspect affected run. |
| Where does a run stall? | Time in each stage, waiting for user, outage, tool failure, repeated question, pending approval, cancelled/blocked terminal reason | Repeated same-scope approval or generic `continue` suggests workflow friction; long human waiting is not agent execution time. |
| Are failures caught before review? | Known failing acceptance checks and their first observed timestamp vs initial reviewer dispatch | Known failures reaching review suggest a handoff/pre-review routing defect. Missing required checks should say `unobservable`, not pass. |
| Does review improve quality or loop needlessly? | Initial/delta review invocations, stable finding IDs, dispositions, correction attempts, unchanged repeated findings, later regressions | Repeated same finding after correction suggests inadequate root-cause recovery; extra reviews with no new evidence suggest review friction. |
| Does context or cost grow without better outcomes? | Tokens by role/phase, cache coverage, repeated file reads, compactions, prompt/capsule size, child restarts, tool error/retry breakdown | Excess cost concentrated in repeated discovery or handoffs suggests a context-packaging issue; never attribute it to Rotta without inspecting the trace. |
| Are we measuring reliably? | Expected vs observed stage events, adapter coverage by host, dropped/duplicate events, unavailable token fields, clock gaps | Missing lifecycle events or host usage must lower confidence; a healthy-looking dashboard with poor coverage is not evidence of health. |

Use a **small, local issue taxonomy** on transitions: `requirement_ambiguity`, `approval_wait`, `environment_or_outage`, `tool_failure`, `host_adapter_failure`, `known_acceptance_failure`, `review_blocker`, `recovery_failed`, `scope_change`, `missing_evidence`, and `unknown`. A code bug can produce `known_acceptance_failure` without implying that Rotta's routing is wrong. A diagnosis always shows work ID, stage, evidence/check/finding IDs, observed symptom and a proposed next experiment; do not store raw prompt or tool output in analytics. Keep source files/evidence referenced from the local work record, not copied into the metric store.

### Local collection and ownership

- Use **one local Rotta-owned store**, initially append-only JSONL under a user-local data directory (outside the repository; e.g. the active XDG data directory's `rotta/telemetry/`), with bounded event schema, version, work ID, event ID, event time, process/host provenance, phase, type, status and optional evidence reference. Use restrictive file permissions; add a local `status`/`report`/`export`/`delete` command and retention setting. No daemon is required: append at accepted checkpoints and read on demand. The default scope is the current machine only.
- **Orchestrator is the authority for workflow transitions.** Its check/handoff/review/terminal events are emitted only after recording accepted evidence for the same work ID and revision. A child returns proposed facts; it does not independently mark the work delivered. A process/event listener may record usage/tool events, but those observations cannot rewrite approvals or acceptance. Store interruption gaps explicitly rather than pretending the missing interval was active time.
- **Host adapters are observers.** Pi can report observed delegation timings and, with a usage hook, parent/child usage; other hosts join only when they expose reliable events. Deduplicate per host event ID and parent/child relationship to avoid counting the same response twice. Clock monotonic duration is valid only within one process; across restarts use persisted wall timestamps with gaps/unknowns, never add overlapping child durations as objective elapsed time. The existing `rotta workflow benchmark` output remains its own immutable fixture format; the new local events should use a new schema rather than changing old results silently.
- **Collection must not obstruct coding.** On unavailable host usage, record `unavailable`/`unsupported` for that field; if checkpoint persistence fails, report the gap instead of fabricating continuity. No network transport, remote collector, background automatic install or uploading local reports is part of this design.

### What the first report should look like

The on-demand CLI report should lead with **eligible work count, evidence coverage, delivered count, first-pass acceptance and median active cycle time** for one comparable mode/host cohort. Next show a stage funnel with drop-off reasons and a table of top diagnosed friction patterns, each linking to **local work IDs** and their evidence references. Drill-down on one work ID should show a timestamped stage/review/check timeline and per-role tool/model/cache accounting with missingness. One task is a case study, not a reliable population trend; with a small sample, show individual runs alongside summary statistics. Default to recent local work with a selectable range; exclude synthetic benchmark fixtures from observed production totals. Example interpretation: “8 started, 5 delivered, 2 legitimately awaiting user approval, 1 stopped after repeated same finding; 4/5 review-eligible runs passed first review; cache-read unavailable for 3/8” is actionable, whereas “success 80%, tokens 2M” is not.

### Closing the improvement loop

Start with evidence-backed **recommendations**, not a policy that edits itself. For each recurring symptom: show affected run IDs and coverage, nominate one change (for example remove an unnecessary approval prompt or tighten pre-review acceptance checks), state what must remain correct, then compare an unchanged representative benchmark corpus before and after that change. Evaluate observed live outcomes only in comparable cohorts and alongside delivered/quality guardrails. Require human review of the diagnosis and any material policy change. This can eventually automate detection and replay, but should not automatically alter Rotta's authority rules based on noisy local metrics.

## Suggested implementation sequence

1. **Fix the measurement contract and local storage.** Define `work-event/v1` as a local append-only stream with work ID, monotonic sequence, event ID, phase, bounded outcome/failure enum, timestamp, host, role, provenance, and source/coverage; pin terminology and metric denominators in tests. Derive funnel/outcomes from events; retain the existing `.rotta/work/<work-id>.md` as workflow continuity, not a fabricated telemetry source. Ensure existing approval/finding history and cumulative review counts survive resumes ([core policy](../assets/core/rotta-core.md)). Start with local on-demand reporting and per-work drill-down; no collector/dashboard service is needed.
2. **Add deterministic, isolated journeys.** Start with Fast one-pass success, Strict approval+success, known failing acceptance before review, initial blocker+repair, persistent blocker+recovery, resume with same findings, missing provider usage, and cancelled/blocked outcomes. Exercise actual supported host/CLI boundaries where possible; tag simulated policy-decision tests separately. Compare the same scenarios on pinned before/after revisions and publish completed/unsupported/failed counts with raw evidence and failure exit status.
3. **Capture observed local runs.** First emit check/review/handoff/outcome transitions from the orchestrator; then add Pi parent/child usage and delegation hooks, and OpenCode, Claude Code, Codex and Copilot CLI adapters as each exposes reliable usage hooks. Export stage boundaries from the orchestrator policy/host event path instead of attempting to reconstruct acceptance from raw token logs. Treat missing hook support as `unsupported`, missing observed value as `unavailable`; report collection coverage by host before cross-host comparison. Avoid storing prompt bodies, code, raw shell output or credentials in metric events.
4. **Compare and recommend, then validate.** Produce per-cohort p50/p90 active time, first-pass and delivered rates, token/cache coverage, review friction and per-stage drop-off with sample sizes; use paired journeys and multiple independent live work samples when available. Rank bottlenecks by attributable active time and unsuccessful transitions, and show run IDs and missingness for each diagnosis. An improvement component may *propose* a policy/role/capsule change, replay the same corpus and compare observed cohorts, and require acceptance/quality guardrails to hold before considering that change. Measurements cannot approve scope, alter authority, or self-promote a workflow policy.

### First useful milestone

A local `rotta workflow report` (or equivalent companion command) can read a handful of versioned work-event fixtures and produce a funnel table, first-pass acceptance, median active cycle time, review friction and **one per-work diagnostic timeline with explicit missingness and provenance**. Pair it with one driven Fast and one driven Strict journey, including a deliberate workflow failure. This provides a real baseline and a way to understand *why* a run failed, without a remote collector, dashboard service or speculative speedup claim; expand to host-level usage only after the local outcome joins are trustworthy.
